## 最少新增结构（开发时再创建）

- src/party/levels.ts：三个关卡的稳定 id、目标、名称、视觉类型、奖励和固定伤害，HP由人数与目标计算。
- src/party/PartySession.ts：纯状态机/事件归约器与数据类型，不直接操作 DOM、摄像头或网络。
- src/party/PartySetup.tsx：2–6人设置、昵称校验与顺序确认。
- src/party/PartyGame.tsx：连接一个摄像头、一个ReadyGate、一个当前计数器，承接派对事件；展示轮换/休息。
- src/party/PartyResult.tsx：本地汇总与贡献；P1增加受限团队战报客户端。
- 仅在新旧界面确有重复时抽取共享 Monster/BattleStage，不预建大型组件框架。原怪物视觉作为森林配置，幽灵/龙是同一组件的轻量SVG分支，不复制计数与战斗流程。

以上为方案阶段的拆分建议；第一批实际文件以[P0第一批本地派对验收](P0第一批本地派对验收.md)为准，后续部分仍为规划。不引入路由、状态管理库、动画库、实时服务或数据库；React状态搭配纯状态机足够。App已按本批授权增加派对入口与共享场景引用。切换旧单人/派对需明确结束进行中的会话，防止同时消费同一帧。

## 数据与状态边界

建议数据：PartySession {partyId, players, levelIndex, phase, activePlayerId, turnId, attemptId, perLevelProgress, rewards, startedAt, endedAt}。Player用随机稳定id、昵称与顺序；perLevelProgress保存每人各关实际次数与pending/active/completed/deferred，不只存显示百分比。生命值、团队合计和贡献由实际次数推导，避免维护几份互相漂移的计数。

主状态：setup → lobby → turnReady → waiting → countdown → active → turnComplete → turnReady；全员完成则 levelWon → 下一关lobby，第三关后 partyWon。paused 可由准备或活动阶段进入；abandoned 表示主动结束且未通关。进入 paused/turnReady/levelWon/partyWon/abandoned 时不得接收计数事件。与 ReadyGate 的内部阶段只做明确映射，不另起并行倒计时。

每次有效计数转换为带 partyId/levelId/playerId/turnId/attemptId/repIndex 的事件。仅当前正式 active 且标识一致、repIndex严格递增的事件可入账；入账一次才播放攻击音与更新怪物。回合达标同步锁定后再渲染动画，避免最后一帧打到下一人。保存当前尝试起始累计次数，使用“尝试基数 + 本计数器序号”记入玩家总数，不能沿用旧App的单局序号比较直接跨人累加。

换人时停止就位门控、废弃旧尝试ID、清空半次动作与站立基线，但保留团队/玩家历史。剩余次数为0时直接进入已完成状态，不创建零目标计数器。摄像头会话可留存，下一人主动准备后才能计数。识别中的worker消息带时间戳，仍保留原过期帧检查；不能仅依赖React渲染完成才能锁回合。

## 跳过、休息和关卡规则

建议：skip = 延后本关剩余目标到队尾，pause = 暂停当前回合。队列每轮记录已延后玩家，连续一轮无人愿继续则停在团队休息，不无限自行轮转。恢复时由主持操作选择当前未完成玩家；不要求额外负担，也不把休息时长作为惩罚。正式开始/恢复仍走原自动就位流程。

示例（合成规则演算，不是真人测试）：2人第一关每人2次。玩家A完成1次后跳过，Boss由40变30；玩家B完成2次，HP变10；A回来补1次，HP变0并解锁第二关。A休息期间不会由B的额外动作代计；若A不再参与，可以结束为未通关，不展示伪造胜利。

每关最多接受 N×目标 个动作，多余动作忽略。伤痕数量不直接使用团队次数无限生成，按受击进度分段映射到有限卡通标记，避免6人Boss反馈溢出；原单人伤痕规则不变。每关只发放一次配置徽章，未击败不发奖励，不以动画结束作为扣血事实来源。

整场经过时间含轮换和休息；不据此判定强弱或称号。不新增精确“运动时长”测量。昵称默认只保存在内存中；离开/刷新可能丢失，提前说明，不暗中启用持久化。

## P1团队战报方案及费用边界

先有PartySummary，再考虑生成。AI仅在三关实际完成后主动触发，按partyId去重，不在每关、每位玩家或重绘时调用；请求失败有明确本地团队评价。个人称号优先由本地规则生成，例如“森林同行者”“从容伙伴”，不使用最快、最慢或健康诊断类称号。

只发送编号和汇总：2–6名玩家、三个固定关卡、整数有效次数、团队总数及经过时间；服务端校验人数/目标/各关和总和一致，不接受自由提示词。昵称不进服务端请求，模型不得决定成绩。保留请求大小限制（优先原2KB，开发时验证紧凑schema能容纳6人三关）、8秒超时、受限输出（优先280tokens）、同场并发去重、失败回退及明确来源。服务器校验只是数据一致性保护，不宣称能证明客户端真实运动。

旧的单人/api/review不改契约；单独规划party接口，分别适配本地服务端与Cloudflare/Vercel包装。公网继续固定返回本地团队战报；新增Key也不得自动打开模型。跨实例可靠总预算未解决前不开放公网AI，不引入付费限流服务。本轮不发出真实模型请求。

## 风险与处理

| 风险 | 影响 | 处理与验证 |
| --- | --- | --- |
| 旧单人常量散在UI/结算/接口 | 改目标后UI和服务端不一致 | 派对独立配置与summary，旧单人契约回归 |
| 换人残留基线或延迟帧 | A的动作计到B | 尝试ID、过期帧、正式阶段检查；换人取消半次动作 |
| 跳过与团队目标冲突 | 无法通关或凭空通关 | 明确延后补足规则，全员跳过可休息/结束，待用户确认 |
| 多人同框与身份不明 | 给错误玩家记分 | 明确只一人入镜、不做人脸识别；不增加同时多人算法 |
| 不同身高/站位 | 新玩家参考姿态不合适 | 每次换人重新校准，沿用宽松计数；必须真人换人验证 |
| 大屏信息过多 | 站远看不清当前玩家 | 保留怪物/摄像头55:45主区，底部只放当前昵称、回合次数与团队HP；完整贡献放回合/最终结算 |
| 语音被重复触发或静音误关联 | 吵闹或无提示 | 保留去抖、测试入口、错误可见；不逐帧读昵称；语音与攻击音开关独立 |
| 无人休息导致快节奏压力 | 用户勉强继续 | 不自动催促、不设速度榜，主动下一位/下一关，无超时惩罚 |
| 公网AI调用与隐私 | 费用或昵称外传 | 公网固定关闭、昵称留本地、只汇总、无视频/关键点/Key入前端 |
| 刷新/浏览器关闭 | 本地进度丢失 | 明确仅内存，尽量提醒；不承诺自动恢复 |
| 新入口或静态资源路径破坏线上 | 原功能不可用 | 先本地与production构建验证，部署需另行授权，模型/WASM/Worker路径保持 |

## 测试规划（第一批已执行项见本地验收记录，后续仍待开发）

1. 配置校验：3关稳定ID、2/3/4目标、2–6人HP公式和奖励；边界2人/6人，拒绝1人/7人及空昵称。
2. 纯状态机：顺序轮换、一次有效事件一次入账/伤害、重复/旧ID/旧序号/旧帧拒绝、回合超额忽略、最后一击只结算一次。
3. 休息/跳过：部分进度保留；休息/倒计时不计数；跳过排队尾；全员跳过不死循环；恢复重建基线；主动结束保持未通关。
4. 三关流转：初始锁第二/三关、不能越级；本关全员完成才解锁；贡献之和与HP一致；三关后只最终结算一次，不自动再开。
5. 合成姿态集成：A下蹲一半换B不加；正式回合浅蹲起立有效、静止不加；摄像头关闭/恢复、换人身高变化后重新校准；演示不能污染真实派对。
6. UI/语音：当前玩家和次数大字、阶段语音去重、测试/静音、普通/大屏进退、昵称按纯文本渲染、重复昵称编号；拒绝授权和模型失败仍可退出/休息。
7. P1接口：2–6人汇总校验、超限/错和拒绝、同场双击去重、超时/错误备用、无Key继续游戏、公网零上游请求；旧单人接口继续通过。
8. 每个代码批次运行既有回归、对应新增测试、类型检查和生产构建。只有依赖、模型路径或部署配置变化时补相应资源检查，不把新增测试数量当作产品效果。
