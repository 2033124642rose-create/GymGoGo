# 第三阶段自动开局排查 · UX-005 · 2026-10-28

## 用户现场现象与证据边界

用户报告：摄像头“识别成功”，站立超过 2 秒仍停在等待就位。没有采集或保存用户视频，也没有现场逐帧关节数据，因此不能声称已确认用户那一次具体是哪个膝盖或哪个关键点触发。

## 代码核查与可复现原因

- 摄像头 assessPose 成功门槛是八个主要关节在 0.02–0.98 画面范围且 visibility >=0.5；准备条件沿用计数测量，范围 0.03–0.97、visibility >=0.65，另需双膝三维角 >=160° 和稳定站位。识别成功本来就不代表站立就位成功，但旧界面没有解释差异。
- ReadyGate 原先直接对原始逐帧膝角、髋部和脚踝作判断。任何一帧不合格都 interrupt，并将累计时间清零；没有滤波，也没有短暂波动容错。
- 修改前先新增三项回归并执行：每 500ms 一帧 159° 膝角、每 1000ms 一帧脚踝可信度 0.64、每 600ms 一帧脚踝横向跳动 0.04。三项均失败，6 秒以上仍为 waiting，复现了用户描述的卡住机制。
- 旧 React 同步只在 phase / digit 变化时刷新，没有展示准备进度与阻塞原因。未发现“始终满足条件仍无法跳转”的独立 React 状态机问题；旧正常站立测试本来通过。

## 修复

1. 仅准备阶段对膝角、髋部与脚踝坐标用最近 3 个有效测量的中位数过滤单帧跳点；160°、0.65、画面边界与稳定位置主阈值均保留，真实 SquatCounter 未改。
2. 在已经取得有效站立数据之后，轻度可信度 / 膝角 / 稳定性波动最多保留 250ms；这期间暂停累计，恢复首帧也不补算不合格时长。超过容忍窗口重新等待，不把零散不合格姿态累计成就位。
3. 人体 / 关节点丢失、出框、三维坐标缺失、严重低置信度、明显弯腿 / 移步立即清空等待或倒计时。断流 >700ms、旧帧、后台页面等原有防护继续保留。
4. 累计 2 秒合格站立后才倒计时；倒计时也暂停轻微波动，丢失则立即取消。准备动作不攻击、通关不重开逻辑继续回归。
5. 主提示显示累计秒数和阻塞原因；开发服务器页面左下角“就位调试”按钮默认折叠，生产构建不显示。面板只读取本地准备帧的数值，200ms 刷新，不存储 / 上传视频或关键点。

面板含当前游戏状态、人体识别是否成功、是否符合站立、具体不满足项、累计时间、原始与滤波后的双膝角、最弱关节可信度、相对躯干的髋 / 脚位移、重置次数与最近原因。正式开局后数值保留为最近准备帧，避免误解为实时计数诊断。

## 2026-10-28 · UX-006：走近读取诊断会改变故障现场

用户仍无法自动计时，并反馈一走近看原因，原因就变了，无法读取远距离失败现场。先前仅提供实时面板让用户反复查看的排查流程不适用。

本轮增加：默认本地内存保存最近 12 条不同的失败快照（原因、膝角、最弱关节可信度、已累计时间），新一轮准备时清空；不保留关键点数组、照片或视频。调试面板支持手动冻结全部诊断状态，包含当时识别状态，避免冻住数值却仍显示现在的人体状态。

远距离诊断：点击后预留 5 秒就位，在随后 10 秒内按 200ms 面板采样，统计主要阻塞原因，并选择该时段有效站立累计最高的快照；结束自动冻结，走近不覆盖。采样次数不是推理帧数或准确率。收起面板取消未完成诊断，手动冻结取消采集，可恢复实时；仅开发环境显示，结果只在页面内存中保留，不上传或写入存储。

本轮保留现有就位与真实深蹲阈值，未凭主观猜测修改。160 度与 0.65 的组合可能在具体取景条件下难以持续满足，但当前没有新的远距离诊断数据证明应调整哪一项；自动计时的真人问题仍未宣称解决。下一步依据冻结报告定位，而非再要求用户在远处读实时小字。
